  怎么做的：原来是一层 CSS 反色框盖在画面上，现在改成在模型渲染完之后再加一道
  WebGL 处理。这道处理只改模型自己的像素，模型之外的区域保持透明，所以页面背景和
  文字不会受影响。

  参考 PV 的做法：
  - 硬切帧：每次故障大约 0.3 秒，由 5～6 个 40～110ms
    的硬切帧组成，帧之间不做过渡，中间夹几帧正常画面，形成一闪一闪的节奏。现在有
    3 套帧顺序，每次随机选一套，看起来不会每次都一样。
  - 横向切片错位：模型被切成高度不一的横条，部分横条左右滑开，还会有零星 2px
    高的细线撕裂。
  - RGB 色散：红、蓝通道左右分开，模型边缘出现彩色描边。横条错位越大，色散越强。
  - 轻微扭曲：一条横向的波浪，加上一段局部鼓起的横带，位置每帧都变，模型看起来像
    被信号拧了一下。
  - 数据条：少数几行模型被切成扁长条，挪到附近的位置。
  - 扫描线：模型表面加一层很淡的隔行暗纹。

❯ 你觉得苹果的那种液态玻璃怎么样                                                

⏺ 液态玻璃可以用，但我不建议照搬苹果的做法。更适合这个页面的是"实验室玻片"式的克
  制用法。

  合适的地方

  - 右侧的模型会从上传框后面穿过：首页的薄片模型是持续转动的 3D
    物体，左边那一环正好会经过左栏下方。玻璃最需要的就是背后有丰富、会动的内容，
    这样折射出来的东西才会活起来，而这里恰好具备。
  - 能解决上一条说的"框像外来物"：玻璃框会映出模型，和右边的画面就连成一体了。

  照搬的问题

  1. 调性冲突：设计规范把模型定为「MATTE · ROUGHNESS
     0.85」，整体是哑光、纸感、硬边的莱茵生命风格。苹果的液态玻璃高光强、偏胶囊
     形、偏消费电子的感觉，大面积使用会显得这一页在模仿 iOS，不像 PV。
  2. 背景大部分是纯色：模型没经过的地方，玻璃下面只有米白底，看起来就是一块普通
     的白框，等于白做了。
  3. 圆角：液态玻璃依赖大圆角和胶囊形状，规范要求圆角不超过 8px。
  4. 网页上很难做像：苹果那种效果的关键是边缘的透镜折射和弯曲，不只是模糊。CSS
     backdrop-filter 只能做到毛玻璃，折射要借助 SVG 位移滤镜，而 SVG 滤镜作为
     backdrop-filter 只有 Chrome 支持，Safari 和 Firefox
     都不行。另外，背景是一直在渲染的 WebGL
     画布，每一帧都要重新模糊，性能开销不小。

  我建议的做法：玻片，不是水滴

  把上一条方案里的设备插槽做成一块厚玻璃片：

  - 形状：小圆角（4–8px）、硬边，保留四角刻度和「01 /
    IMPORT」标签，像实验室里的载玻片。
  - 折射放在 WebGL 里做，不用 CSS：上次做故障效果时已经有了一道后期处理。可以把
    上传框在屏幕上的位置传给着色器，在这个矩形里做几件事：
    - 对模型做轻微的透镜折射，边缘处更强，像厚玻璃的倒角；
    - 加一点模糊和色散，色散只出现在边缘；
    - 顶边加一条 1px 的高光。

    这样所有浏览器效果一致，几乎没有额外开销，因为画面本来就在这一步渲染。DOM
    那边只负责文字和按钮，框体本身透明。
  - 好的副作用：模型的薄片经过玻片时会被"放大和扭曲"，这种动态是苹果式液态玻璃也
    给不了的，又和刚做的信号失真属于同一套视觉。
  - 手机端：模型在上传框上方，两者不重叠，玻片退化为细线框即可。

  如果你就是想要苹果那种圆润、偏亮的液态感，也能做，只是我认为它会和右边的哑光雕
  塑打架。

  要我按"玻片"方案做一版吗？先出静态和模型穿过时的截图给你看，不满意再改。

❯ 你觉得首页加点线条HUD怎么样，就是那种明日方舟不是经常喜欢用一些简单的几何图像 
  或者直线做点缀，我不知道怎么讲                                                

⏺ 可以加，而且很适合这个页面。你说的应该是明日方舟 UI
  里那类"工业制图"式的装饰：细长直线、十字定位标、刻度尺、小方块、斜纹警示条、残
  缺的圆弧、编号和小字代码。它们不传达具体信息，作用是让画面像一张有精确度的技术
  图纸，正好对上现在首页的「标本 + 玻片」方向。

  关键：克制

  方舟的线条之所以好看，是因为少而准。大致几条原则：

  - 只用 1px 细线，颜色用墨色的 20%～40% 透明度，橙色只在 1～2 个点上出现。
  - 全部对齐到 48px 网格，这是工作台本来就有的网格。
  - 放在边缘和空白处，不压标题，不压上传框。
  - 每个装饰都和画面里的东西有关系：要么指向模型，要么框住某个区域，要么在边缘做
    刻度。随手散落的几何图形会显得廉价。

  我建议加的几样

   ─────────────────────────────────── ✛ ──────── 0x2F · SPECIMEN
                                            ╭─ ─ ─╮
    画面之内。                          ╱    ∞    ╲ ← 残缺圆环, 缓慢反转
    答案之间。                         │  ┼        │

  SHEETS 500
                                         ╰─ ─ ─ ╯           TWIST 0.15 RAD/S
    01 / IMPORT
    ┌ glass slide ┐                                          ▮▮▯▯▯
    └────────────┘
   |''''|''''|''''|''''|''''|''''|''''|  ← 底部刻度尺        ////// ← 斜纹块

  1. 模型的瞄准环：围绕模型中心画一个只有几段的残缺圆弧，加十字准星，非常缓慢地
     反向转动，像在"锁定标本"。这是最有方舟味道的一样。
  2. 引线 + 标注：从模型上的某一点拉一条折线到右侧空白处，末端写等宽小字，比如「
     INFINITY / SHEETS 500 / TWIST 0.15
     RAD/S」。引线起点跟着模型实时移动（每帧从 3D
     坐标投影到屏幕），这样线条和模型是"连着"的，不是贴上去的。
  3. 顶部长横线：横贯页面的细线，中间带一个十字标和编号，像图纸的边框线。
  4. 底部刻度尺：沿下边缘一排短刻度，每 5 格一根长刻度，最右边一小块斜纹警示条。
  5. 零散的小件：一两个小实心方块、一组 >>> 箭头、一个竖排编号，放在角落里。

  动效：首次进入时，线条按顺序"画出来"，用 stroke 描线动画，0.6～1s。之后只保留
  圆环的缓慢转动和引线跟随，别的都静止。上次做的故障失真触发时，HUD
  也可以跟着闪一两帧，这样两套效果是联动的。

  手机端：只保留引线和底部刻度，其余隐藏，不然会挤。

  实现

  用一层全屏 SVG，不拦截鼠标，颜色全部取自 token，描线动画用
  GSAP。引线起点需要模型把 3D 点投影后的屏幕坐标传出来，在现有的 SculptureCanvas
  里加几行就行。减少动态效果开启时，直接显示静态线条。

  要做的话，我建议先做 1、2、4
  三样：瞄准环、引线标注、底部刻度。做完截图给你看，再决定 3 和 5 要不要加。

  你旧实现不稳定的原因

  解析这一步（bilibili_adapter.py、acquisition.py）：
  - 依赖第三方库的匿名调用：主路线是 bilibili-api 库的匿名请求，没有自己处理 B
    站的风控要求（设备标识 buvid、WBI 签名），所以经常被风控拦截，返回 412
    错误。代码注释里也提到了这一点。
  - 时长校验太严：播放时长和分P时长差超过 1 秒就判失败，理由是"可能为试看"。
  - 只认一个地址：B 站一般会给出主地址加若干备用地址（不同 CDN
    节点），旧代码只用主地址，没有换节点重试。

  抽帧这一步（media.py 的 prepare_stream）是"抓不全就失败"的直接原因：
  - 一条命令顺序读完整个视频：用一次 ffmpeg 从头解码整条远程流。网络抖一下、CDN
    断流，或者地址签名过期（B
    站地址大约两小时有效），整次解析就失败，已经抓到的帧也作废。
  - 全有或全无的校验：有三处：最后一帧离结尾超过一个间隔就报错（"媒体提前结束"）
    ；图片数量和时间戳数量对不上就报错；一帧都没有就报错。
  - 音频也会拖垮全局：音频和画面一起读，音轨短了也算失败。

  实测结果（在这台机器上，匿名，不登录）

  用 B 站第一个公开视频（av2，约 34 分钟）测试：
  - 解析能拿到地址：先获取设备标识 buvid，再用 WBI
    签名请求视频信息和播放地址，都返回成功。DASH 视频流匿名能拿到
    360p/384p，用来抽帧分析足够；每条流还附带 1 个备用地址。
  - 两种地址的限制不同：DASH 地址必须带 B 站的 Referer 请求头，否则返回
    403。另一种 platform=html5 的 MP4 地址不带 Referer 也能读。
  - 按时间点独立抽帧可行：均匀取 24 个时间点，每个点单独让 ffmpeg

    5.6 秒，总共 25 秒。

  所以思路是成立的：不用下载整个视频，每一帧都是独立的小请求，某一帧失败也不影响
  其他帧。

  BiliDown 这类工具之所以稳，做法基本就是这几样：自己处理设备标识和签名、在多个
  CDN 节点之间切换、地址过期了重新获取，另外可以扫码登录拿更高画质。

  方案

  1. 链接解析：自己写一个轻量的 B 站解析器

  - 链接归一：支持 BV 号、av 号、b23.tv 短链（先跟随跳转）、?p=
    分P、手机版链接。
  - 请求流程：获取 buvid → WBI 签名（签名密钥按天缓存） →
    视频信息（标题、时长、封面、分P、cid） → 播放地址（优先 AVC 编码、不超过
    720p），把主地址和所有备用地址都存下来。
  - 三层兜底：DASH 地址失败就换 html5 MP4 地址；再不行用 yt-dlp。
  - 地址过期处理：地址只放在内存里，记录过期时间，过期了自动重新获取。
  - 扫码登录（可选）：像 BiliDown 那样扫码登录，可以拿到更高画质，也更不容易被风
    控。抽帧分析其实不需要高画质，所以匿名就够用。
  - 暂不支持的内容：番剧、付费、充电专属视频暂不支持，遇到时给出明确提示，而不是
    笼统的"解析失败"。

  2. 抽帧：按时间点独立抽取，先粗后细

  - 先粗：先均匀抽 16 帧，大约十几秒就能进入对话。
  - 再细：后台继续补到 48～64 帧，之后还可以在画面切换处补帧。
  - 每帧独立重试：顺序是换备用 CDN 节点 → 重新获取地址 →
    还不行就放弃这一帧，记为缺口。
  - 逐帧推送：每抽到一帧就推给前端，现在的界面本来就是一帧一帧显示出来的。
  - 音频单独处理：音频（以后做语音识别用）和画面分开，失败了不影响画面。

  3. 帧不全也能对话

  - 记录覆盖情况：例如"已获取 41/64 帧，缺失 03:20–04:10"。
  - 进入对话的门槛很低：只要有 1 帧就能对话。
  - 一帧都没有时：仍然可以基于标题、简介和 B 站的 CC
    字幕对话，并明确标注"未取得画面"。字幕对理解视频内容其实很有用。
  - 告诉模型哪里缺：覆盖情况会写进给模型的上下文。用户问到缺失的时间段时，回答会
    说明"这一段没有取到画面"，而不是编造。
  - 时间轴上的显示：缺失的帧显示成空心或斜纹薄片，不能选中。提供「补抓缺失片段」
    按钮，对话进行中也可以后台补帧。

  4. 前端

  - 输入：首页玻片支持直接粘贴链接，自动识别是链接还是本地文件。
  - 解析过程：上传屏改成显示解析步骤：识别链接 → 获取视频信息 → 获取播放地址 →
    抽帧 n/64。
  - 帧不全时：显示一条提示条，不阻断流程，可以直接进入对话。

  5. 后端

  backend 目录现在是空的。我建议用 Python + FastAPI：你旧项目就是 Python 和
  uv，里面一些好的思路可以直接借鉴，比如身份校验（确认拿到的就是目标视频）和读取
  失败后重新获取地址。接口草案：
  - POST /api/links/resolve：输入链接，返回视频信息和分P列表。
  - POST /api/videos/from-link：开始抽帧，通过 SSE 实时推送每一帧和覆盖进度。
  - POST /api/videos/{id}/frames/retry：补抓缺失的时间段。

  合规上：只取帧做分析，不保存完整视频，只处理公开视频。

  需要你定的几件事

  1. 扫码登录：要不要做？我建议先只做匿名，登录以后再加。
  2. 后端技术栈：用 Python + FastAPI 可以吗？
  3. 平台范围：这次先只做 B 站，抖音等平台之后再接，可以吗？

  你确认后，我按这个顺序做：B 站解析器（加单元测试） → 逐帧抽取和覆盖率 →
  前端接入链接输入和不完整状态 → 补抓功能。
